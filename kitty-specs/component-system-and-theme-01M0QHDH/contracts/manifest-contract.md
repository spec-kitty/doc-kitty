# Contract: the merged virtual manifest

How the resolved theme's `slots` + `layouts` reach the carriers. Delivered as an Astro
integration-generated virtual module (`research.md` Decision 1).

## Module

```ts
// virtual:doc-kitty/manifest  (generated at astro:config:setup from the merged theme)
export function resolveLayout(kind: string | undefined): LayoutComponent; // sync; Default fallback
export const slotComponents: Partial<Record<DkSlotName, Component>>;       // per-carrier lookup
```

- Generated by statically importing each merged `kind → path` and `dkSlot → path`, so
  render-time resolution is a synchronous map lookup — **no** runtime dynamic import.
- `resolveLayout` preserves the exact M1 signature `(kind) => LayoutComponent`, so the
  `MarkdownContent` carrier body does not change (ADR-0015 decision 1, seam 1).

## Resolution rules

| What | Where | Rule |
|---|---|---|
| `kind → layout` | single `MarkdownContent` import site | manifest lookup; unknown/absent → `Default`; validator warns (ADR-0009) |
| `dk:head`, share metadata | `Head` carrier | reads `slotComponents` for its slots |
| `dk:page-hero`, `dk:metadata-band` | `PageTitle` carrier | reads `slotComponents` for its slots |
| `dk:audience`/`dk:related`/`dk:external-references` | `MarkdownContent` carrier | **M3** — host points exist, unwired in M2 |
| `dk:site-footer` | `Footer` carrier | reads `slotComponents` |
| non-carrier pass-throughs (Header, SiteTitle, Banner, …) | — | **sequenced past M2** (ADR-0015 decision 4); not registered as `components` entries |

## No-theme (degenerate) case

With no theme the generated manifest equals the M1 static module: `Hub` registered,
every other `kind` → `Default`, no slot overrides. The carrier reads it identically.
