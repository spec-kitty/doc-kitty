# Mission Specification: QOL Adoption-Enabler Cluster

**Mission Branch**: `feat/qol-adoption-enablers`
**Created**: 2026-08-31
**Status**: Draft (rev2 — sharpened after post-spec brownfield squad)
**Input**: Four brownfield GitHub issues (#38, #40, #41, #44) surfaced by the spec-kitty adoption study (`docs/architecture/research/spec-kitty-adoption-proof.md`), plus locked owner decisions captured in `scratchpad/GROUNDING-BRIEF.md`.

**rev2 changes** (post-spec adversarial squad, 3 lenses): resolved a load-bearing topology error (doc-kitty's own `docs/adr/README.md` is **never** Astro/Hub-rendered — only `example/docs/` is built), so the ADR index is generated by a **script + lockfile-style sync-check** for the own tree and by the **Hub** for the example tree; scoped FR-006 to a **targeted per-page correction** (keep `Feature` a valid type; no derivation-subtype change); made FR-004 own "override resolves against **derived** types"; pinned FR-003/FR-007 acceptance to non-fakeable assertions; reworded NFR-001; reconciled FR-009 with the amended contract; count corrected to **19**.

## Context & Intent Summary

doc-kitty is a reusable Astro+Starlight documentation toolkit. A demanding real adopter (the spec-kitty proving ground) surfaced quality-of-life gaps that also fix doc-kitty's own inconsistencies. This is a **split-goal** mission bundling four independently-valuable adoption enablers that share the `_meta/` registry + `validate-frontmatter.mjs` + `metadata.ts` surface:

- **#38** — make `type`/`kind` frontmatter optional (derive `type` from the section registry).
- **#40** — make the `type`/`kind` vocabulary overridable per-consumer (neutralize the forbidden `Feature` term, applied to authored *and* derived values), and correct doc-kitty's own genuinely-misplaced pages (targeted; `Feature` stays valid).
- **#44** — doc-honesty: generate the ADR index instead of hand-maintaining it; fix stale `AGENTS.md` and README claims.
- **#41** — tolerate era-partitioned ADR paths (`adr/<era>/NNNN-`) — already works; pin it with a guard.

**Primary actor**: a documentation-toolkit *adopter* (an engineer migrating an existing large corpus onto doc-kitty) and, secondarily, doc-kitty's own maintainers dogfooding the convention.

**Explicitly out of scope (deferred to Mission B)**: the README-enforced + `README.md → index.md` symlink / double-render loader hardening. That work carries a live build crash and cross-platform concerns and will be its own mission.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Optional type/kind frontmatter (Priority: P1)

An adopter with a large existing corpus (hundreds of docs) onboards to doc-kitty without being forced to hand-add two required frontmatter fields (`type`, `kind`) to every file. When a file omits `type`, the toolkit derives it from the file's registered section; when a file omits `kind`, that is accepted (no derivation). An explicitly authored `type` is always honored; if it disagrees with the section-derived type, the author gets an advisory warning, not a hard failure.

**Why this priority**: This is the single largest raw authoring cost an adopter faces and the lowest-risk change (the site zod schema is already optional — only the standalone gate is strict). It unblocks corpus onboarding.

**Independent Test**: Run the standalone frontmatter validator against a fixture doc that omits `type` and `kind` under a registered section → passes (`problems == []`), with `type` reported as the section-derived value. A fixture that authors a conflicting `type` → `problems == []` **and** the structured `warnings[]` contains the specific mismatch entry (asserted on the return value, never on console text).

**Acceptance Scenarios**:

1. **Given** a doc under a registered section with no `type` and no `kind` in frontmatter, **When** the standalone validator runs, **Then** it passes and the effective `type` equals the section's registry-derived type.
2. **Given** a doc that authors `type: Reference` while its section derives `Explanation`, **When** the validator runs, **Then** it passes, honors `Reference`, and emits an advisory (non-failing) mismatch warning.
3. **Given** a doc with no `type` that lives outside any registered section (root/orphan, where derivation yields nothing), **When** the validator runs, **Then** behavior is deterministic and documented (see Edge Cases) rather than a crash.

### User Story 2 - Overridable vocabulary + self-consistent corpus (Priority: P1)

An adopter whose governance forbids a term doc-kitty ships (`Feature`, forbidden by a Mission-canon charter) can alias, neutralize, or forbid that term through a declarative, on-disk override so no document is ever *required* to emit it — whether the term was **authored** or **derived** from the section registry. The override resolves `default → consumer` and is read by the standalone gate without needing an Astro build. Separately (and independently), doc-kitty corrects its own genuinely-misplaced pages: `Feature` remains a valid doc-kitty type, but any page under `docs/plans/features/` whose *content* is not actually a feature (e.g. a mission/portal topic) is corrected so its authored type matches its section-derived type with **zero** residual path-mismatch warnings.

**Why this priority**: `Feature` is a hard adoption blocker for the reference adopter (CI-enforced forbidden term). The override is the mechanism that unblocks them. doc-kitty's own corpus correction is a targeted dogfood-honesty fix, not a vocabulary change — `Feature` stays a legitimate default term.

**Independent Test**: With a `_meta/vocabulary.yaml` that forbids `Feature`, run the standalone gate against a doc emitting `Feature` (authored **or** derived from `plans/features/`) → fails with a clear override-driven message; against the aliased replacement term → passes; with no override file → default vocabulary unchanged. Separately, run the gate over doc-kitty's own corpus → zero authored-vs-derived path-mismatch warnings on `docs/plans/features/`.

**Acceptance Scenarios**:

1. **Given** a consumer `_meta/vocabulary.yaml` that aliases `Feature → Mission`, **When** a doc authors `type: Feature`, **Then** the toolkit applies the override so the adopter is never forced to emit the raw forbidden term.
2. **Given** the override marks `Feature` forbidden, **When** the standalone gate validates a doc emitting `Feature`, **Then** it fails with a message naming the override and the allowed replacement.
3. **Given** the override aliases `Feature → Mission` and a `plans/features/` page that authors **no** `type`, **When** the gate runs, **Then** the *derived* `Feature` resolves through the override to `Mission` (not a warning, not raw `Feature`) — the override reaches derived values, not only authored ones.
4. **Given** no `_meta/vocabulary.yaml` is present, **When** the gate runs, **Then** the shipped default vocabulary applies unchanged (full backward compatibility) and `Feature` remains valid.
5. **Given** doc-kitty's own corpus after the targeted correction, **When** the frontmatter gate runs, **Then** no `docs/plans/features/` page emits a *new* authored-vs-derived path-mismatch warning, each in-place-corrected page's `kind` semantically matches its content (`type` stays `Feature`), and any genuinely type-misplaced page is filed as a relocation follow-up (C-006a) rather than re-typed in place.

### User Story 3 - Self-generating ADR index and honest project docs (Priority: P2)

A reader (or an agent) sees an ADR index that is always complete because it is *generated from ADR metadata*, not hand-maintained. Because doc-kitty's own `docs/` tree is **not** rendered by Astro (only `example/docs/` is built), the own-tree index is produced by a generator script whose output is committed and kept honest by a lockfile-style sync-check; the example tree — which *is* Hub-rendered — drops its redundant table and lets the Hub demonstrate auto-listing. Adding a new ADR requires no manual index edit in either tree. Cross-references pointing at a non-existent ADR are caught automatically. `AGENTS.md` and the READMEs describe the system as it actually is (correct field names, full section list, the amended optional-frontmatter contract, shipped toolchain) without overclaiming.

**Why this priority**: The ADR index has silently drifted more than once (ADR-0030 landed unindexed — in the *own* tree, precisely where no renderer runs). A generator + sync-check closes that drift class by construction for the tree where it actually happens. The stale AGENTS.md/README claims are a doc-honesty defect a first adopter reads first.

**Independent Test**: Own tree — add a throwaway ADR fixture, run the generator: the committed table gains a number-ordered row with its Status/Date, and the sync-check fails if the table is left stale. Example tree — add an ADR fixture and build: the rendered `/adr/` HTML contains a link to it (asserted against built output, not a source grep). Referential integrity — a valid ADR reference passes and a dangling one fails the same check. Inspect AGENTS.md/README → no stale `status` field, full section list, the amended optional-frontmatter contract, no "early scaffold" claim.

**Acceptance Scenarios**:

1. **Given** doc-kitty's own `docs/adr/README.md` (never Hub-rendered), **When** a new ADR file is added and the ADR-index generator runs, **Then** the committed table is regenerated from ADR frontmatter + body `## Status` — number-ordered, with Status and Date — and a CI sync-check fails if the committed table does not match a fresh regeneration.
2. **Given** the Hub-rendered `example/docs/adr/`, **When** a new ADR fixture is added and the site is built, **Then** the rendered `/adr/` index lists it automatically and the previously-redundant hand table in `example/docs/adr/README.md` no longer exists (asserted against built HTML).
3. **Given** an ADR references another ADR by id/path, **When** the referential-integrity check runs, **Then** a reference to a non-existent ADR **fails** and a valid reference **passes** (both polarities asserted in one test).
4. **Given** the current `AGENTS.md`, **When** this mission completes, **Then** it references `doc_status` (not `status`), enumerates all sections declared in `_meta/sections.yaml`, and describes the **amended** contract — `type` optional/registry-derived and `kind` optional — rather than the pre-mission "required" posture.
5. **Given** the current `README.md` and `src/README.md`, **When** this mission completes, **Then** the "early scaffold / before the build toolchain is wired up" framing is replaced with an accurate description of the shipped toolchain, while the licensing status (UNLICENSED) is stated truthfully and not overclaimed.
6. **Given** `docs/context/convention.md` states decision status lives "in the ADR body and the `adr/README.md` table", **When** the table becomes a generated artifact, **Then** that convention text is updated in the same change (living-docs sync).

### User Story 4 - Era-partitioned ADR trees keep ADR typing (Priority: P3)

An adopter with a large ADR history organizes ADRs under era subfolders (e.g. `adr/3.x/0001-…`). Those files continue to be typed `ADR` without flattening the tree. This already works via the section's first-path-segment type switch; the mission pins it with a regression guard so a future refactor cannot silently break it.

**Why this priority**: Lowest effort (guard-only) and lowest risk, but valuable insurance against a class of regression that would surprise a large adopter.

**Independent Test**: A fixture at `adr/3.x/0001-foo.md` resolves to `type: ADR`; a fixture at `adr/3.x/template.md` resolves to its basename-keyed subtype. A regression test pins both on the ts and mjs derivations. Consistency check: the own-tree ADR-index generator (FR-007) walks ADR files **recursively**, so an `adr/<era>/` ADR also appears in the generated index — the generated index and the era-tolerant typing do not contradict.

**Acceptance Scenarios**:

1. **Given** an ADR file at any path depth under `adr/` (e.g. `adr/3.x/0007-foo.md`), **When** type derivation runs, **Then** it resolves to `ADR`.
2. **Given** the ADR path→type mapping, **When** the mission's changes land, **Then** the mapping is **not** rewritten to a broad `adr/**` glob (guard-only; avoid over-matching non-ADR content).

### Edge Cases

- **Type derivation is not total.** A doc with no `type` that lives at the repo root or under an unregistered/orphan section has no section to derive from. Required behavior: the validator must handle the absent-derivation case deterministically — either accept with an explicit "untyped" outcome or fail with a clear, actionable message — never crash or emit an empty/garbage type. The chosen behavior must be documented in the amended ADR.
- **Authored-vs-derived conflict.** Authored `type` wins; mismatch is advisory-warn only (never a hard failure) — preserving today's ADR-0004 behavior. The warning must be emitted through the validator's **structured** return (`warnings[]`), so a test can assert it fired without coupling to console text.
- **Vocabulary override + derivation interaction.** When both an override and a section-derived type apply, the override resolves against the *effective* (possibly derived) type; an aliased/forbidden term must be enforced whether the term was authored or derived. The override transform must be applied at **both** the derivation switch and the authored-value path, and in **both** the mjs gate and the ts schema, so the two twins resolve identically.
- **`kind` has no registry equivalent.** For `kind`, "optional" means optional only — there is no derivation source; an absent `kind` is simply accepted.
- **ADR index — two trees, two mechanisms.** doc-kitty's own `docs/adr/` is never Astro-rendered, so its `README.md` table is a **generated artifact** (script regenerates it from ADR frontmatter + body `## Status`; committed; sync-checked). The `example/docs/adr/` tree *is* Hub-rendered, so its redundant table is deleted and the Hub auto-lists. Known Hub limitation for the example tree: the Hub sorts children alphabetically-by-title (not ADR number) and cannot surface body-only `## Status` — acceptable for the single-ADR demo; a general "ADR-number-ordered, status-aware Hub card" is a filed follow-up, not this mission.
- **ADR index information fidelity (own tree).** The generator preserves the ID/Title/Status/Date columns the hand table carried (Status parsed from the ADR body `## Status`; Date from frontmatter `updated`), so no information is lost on the tree humans actually read on GitHub.
- **Missing/optional `_meta/vocabulary.yaml`.** Absent file → shipped defaults (`Feature` stays valid); malformed file → clear validation error, not a silent fallback.
- **Own-corpus correction must not mistype content.** `Feature` stays a valid type; a `plans/features/` page is corrected only when its *content* is genuinely not a feature. Correction makes authored == derived (re-type where the current type is simply wrong, or relocate a single genuinely-misplaced page). A full `plans/features/ → plans/missions/` folder rename (route/link churn) is explicitly out of scope (Mission-B-adjacent; filed as a follow-up).

### Key Entities

- **Section registry** (`docs/_meta/sections.yaml`, `example/docs/_meta/sections.yaml`): declares sections and their `expectedType`; the authority from which absent `type` is derived.
- **Vocabulary override** (`_meta/vocabulary.yaml`, new): declarative `type`/`kind` aliases, neutralizations, and forbidden terms; resolved `default → consumer`; readable by the standalone gate without a build; applied to authored **and** derived values, mirrored across the mjs gate and ts schema.
- **Frontmatter contract**: the `type`/`kind` fields and their validation across three layers (standalone `validate-frontmatter.mjs` gate, site zod schema, `metadata.ts` derivation).
- **ADR-index generator** (new script): reads the ADR files (frontmatter + body `## Status`) and regenerates the own-tree `docs/adr/README.md` table (number-ordered, ID/Title/Status/Date); a CI sync-check verifies the committed table is regeneration-clean.
- **ADR index (two trees)**: `docs/adr/README.md` — generated artifact (own tree, never Astro-rendered); `example/docs/adr/README.md` — table removed, `kind: Hub` auto-lists (rendered tree).
- **Decision records**: ADR-0004, ADR-0009 (amended); a new vocabulary-override ADR; the #44 generator/two-tree decision note.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A documentation file authored with neither `type` nor `kind`, under a registered section, passes the standalone validator with the effective type equal to the section-derived type (passing fixture test).
- **SC-002**: With a consumer vocabulary override forbidding `Feature`, no document is required to emit `Feature` — whether authored or derived from `plans/features/`; a doc emitting it fails with an override-driven message and the aliased replacement passes; with no override file, `Feature` stays valid (fixture tests across all three cases).
- **SC-003a (own tree)**: Adding an ADR file and running the generator produces a number-ordered `docs/adr/README.md` row carrying its Status and Date; leaving the committed table stale fails the CI sync-check.
- **SC-003b (example tree)**: Adding an ADR fixture and building the example site makes it appear in the rendered `/adr/` HTML with no manual table edit (asserted against built output, not a source grep); no hand table remains in `example/docs/adr/README.md`.
- **SC-004**: A broken ADR cross-reference fails and a valid one passes the same automated referential-integrity check (both-polarity fixtures).
- **SC-005**: A reviewed classification of all 19 `docs/plans/features/` pages is committed; every in-place-corrected page's `kind` semantically matches its content (`type` stays `Feature`); genuinely type-misplaced pages are filed as relocation follow-ups; **no new** path-mismatch warning is introduced (guard, not proof). Separately, `AGENTS.md` and the READMEs contain none of the identified stale claims and AGENTS.md describes the amended optional-frontmatter contract.
- **SC-006**: ADR files under an era subfolder (`adr/<era>/`) remain typed `ADR`, pinned by a regression test on **both** the ts and mjs derivations that fails if depth-tolerance is lost.
- **SC-007**: The full pre-existing CI gate set passes; no previously-passing document regresses; no test is deleted or weakened to make the suite green (NFR-001/NFR-002).
