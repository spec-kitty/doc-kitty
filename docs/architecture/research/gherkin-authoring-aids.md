# Gherkin authoring aids and the Specification layout (research)

Three follow-ups to the Gherkin work were split from
[#130](https://github.com/spec-kitty/doc-kitty/issues/130):

- [#196](https://github.com/spec-kitty/doc-kitty/issues/196) asks for an opt-in,
  warn-only check that flags steps describing UI mechanics.
- [#197](https://github.com/spec-kitty/doc-kitty/issues/197) asks for
  `gherkin.defaultContext`, a map from source folder to glossary context.
- [#198](https://github.com/spec-kitty/doc-kitty/issues/198) asks for a
  dedicated Specification layout for feature pages.

This note records the evidence each one rests on, the design options, and the
decisions that must be made before a mission can be specified. It is research,
not a decision. Each choice it recommends still needs the operator's call, and
the choices that change a contract need an ADR.

## Method and evidence limits

A five-lens pre-spec squad ran in parallel, following the
`adversarial-squad-deployment` procedure. The lenses were prior art, step
wording, architecture, layout design, and requirements analysis. Every finding
cites a file and line in this repository or an external source. Where two lenses
disagreed, the orchestrator settled it from the source, and the result is noted
inline.

Two limits apply:

- **Profiles were read, not resolved.** The spec-kitty CLI was not installed
  when the squad ran, so each delegate read its profile YAML directly. That is
  the procedure's documented fallback, but it does not apply overlays or
  `specializes_from` lineage.
- **Some vendor sites were unreachable.** DNS failed for cucumber.io,
  starlight.astro.build and serenity-bdd.github.io. Prior art was read from the
  upstream repositories instead, and Starlight from the pinned 0.42.6 in
  `node_modules`.

Main was at `b22df06` (Astro 7.4, Starlight 0.42.6, the `unified()` processor
of [ADR-0060](../../adr/0060-markdown-processor-unified-for-astro-7.md)). None
of the three issues touches remark plugin order. #196 and #197 sit in code
generation and the existing fence stage, and #198 is component-level, so
ADR-0060 has no bearing on any of them.

## Ground truth shared by all three

- **Code generation runs once, in config setup.** The integration calls
  `loadFeatures` and then `generateFeaturePages` in `astro:config:setup`
  (`src/lib/integrations/gherkin.ts:82-98`). The pages are committed and
  drift-gated by the CLI twin, run as `pnpm validate:features`
  (`src/scripts/generate-feature-pages.mjs:295-312`, `package.json:24`).
- **Warnings are callbacks, not a sink.** `errors.mjs` holds fatal errors only
  (`src/lib/gherkin/errors.mjs:1-30`). Each path prints warnings differently:
  `logger.warn` in code generation (`gherkin.ts:84`), `console.warn` in the
  fence stage (`gherkin-fence.ts:438`), and `⚠` lines from the CLI
  (`generate-feature-pages.mjs:276`). Only drift changes the CLI exit code.
- **A view-level check already exists.** `warnDuplicates(view, {file, warn,
  lineOffset})` (`src/lib/gherkin/render.mjs:520-545`) runs from
  `renderFeatureBody` for generated pages (`:599`) and directly for fences
  (`gherkin-fence.ts:532`). Includes pass a no-op `warn`
  (`gherkin-fence.ts:629-631`).
- **The CLI must mirror the page options.** Every key in `GHERKIN_PAGES_KEYS`
  (`src/lib/gherkin/options.mjs:39-52`) needs a CLI flag, and
  `src/tests/gherkin-example.test.ts:125-131` enforces that. Without the flag,
  `validate:features` cannot reproduce the bytes. Options that do not change
  generated bytes belong in `GHERKIN_OPTION_KEYS` instead, and an unknown key is
  a hard error (`options.mjs:380-388`).
- **Layouts already dispatch by `kind`.** A layout is chosen from `kind` in one
  place, the `MarkdownContent` carrier (`src/components/MarkdownContent.astro:54-58`),
  through the theme manifest. Only `Hub` is a base kind
  (`src/lib/manifest.ts:72-74`), so generated pages, which carry
  `kind: Specification`, fall back to `Default`.

## #196 Imperative-step lint

### The problem

ADR-0046 already promises this:

> Imperative, UI-level scenarios read poorly as docs. Mitigated by authoring
> guidance; a lint is a follow-up.

That is at `docs/adr/0046-gherkin-feature-pages.md:160-161`. The authoring guide
gives bad examples (`docs/guides/authoring.md:300-317`) and says "Nothing checks
for them yet". That sentence becomes false when this lands.

### Prior art

- **No maintained Gherkin linter ships an imperative-step rule.** gherkin-lint
  and its fork gplint have `no-restricted-patterns`, but no default verb list.
  gplint's shape is the model to copy (`gplint/src/rules/no-restricted-patterns.ts:27-30,121-143`):
  - patterns are case-insensitive regexes;
  - patterns are grouped per keyword (`Given`, `When`, `Then`, `Step`);
  - `And` and `But` inherit the preceding keyword's list;
  - severity is `off`, `warn` or `error`.

  Neither tool has inline disable comments; both ignore whole files only.
- **cuke_sniffer has an "implementation word" rule.** Its list is page, site,
  url, dropdown, click, text box, radio button, check box, window, pop-up,
  screen and database. It matches by substring, so "website" and "opposite"
  trip it, and it has no suppression. It is a warning of what not to do.
- **Cucumber's guide argues for the rule but not for a hard stop.** It says
  declarative steps read better as living documentation, but imperative ones
  are "appropriate" in some contexts. Its examples include `press` and `type`
  (`better-gherkin.md:41-43,82`). That supports off by default and warn-only.
- **Vale is the wrong engine, despite being in the repo.** A warning-level Vale
  rule is filtered out by the `--minAlertLevel=error` gate
  (`.github/workflows/ci.yml:142`). It would also report `.md` lines rather than
  `.feature` lines, and it cannot see keyword type, placeholders or quoted
  arguments. Only its list format is worth borrowing.

### Wording: what the default list should hold

For a docs site, some UI verbs are domain language. The consumer fixture's
student "opens" a chapter and "hovers over" a term
(`tests/consumption/consumer-fixture/scenarios/study/read-a-chapter.feature:11,17`).
A broad list will produce false positives, so the default should stay
conservative.

| Entry (all inflections) | False-positive risk | Counter-example |
|---|---|---|
| click, double-click, right-click, tap, hover, scroll, drag | low | "tap the reserve" (finance) |
| `fill in` / `fill out` | low | "fill in for a colleague" (HR) |
| `navigate to` (with "to") | medium | "the system navigates the route" |
| `type … into` (verb shape only) | medium | "the leave type" |
| `press … button/key` | medium | "press charges", "press release" |
| `visit … page/URL` | medium | "the inspector visits the warehouse" |
| `refresh/reload the page`, `check/uncheck … box` | low as phrases | bare "check the balance" |
| enter, select, submit, open, bare UI nouns | high | "enters a contract", "select a plan", "submit the declaration" |

The prior-art lens proposed a wider default that includes `enter` and `select`.
The wording lens showed that both fire on the example's own domain language. For
example, `submit` fires on `example/features/shipping/declare-customs.feature`.
The orchestrator sides with the narrower list. The high-risk entries should be
documented as known-ambiguous, for a consumer to add through `extend`.

A selector check is a separate, cheap signal. A quoted argument shaped like a
CSS selector (`#id`, `.class`, `[attr=`) is the guide's own bad example.

### Design options

| Option | Where it runs | Trade-off |
|---|---|---|
| A. Code generation only | inside `renderFeatureBody` | Covers `astro build` and `validate:features` alike, but misses in-page fences |
| B. Fence stage only | beside `warnDuplicates` in the fence | Misses `.feature` sources. The content-layer cache skips unchanged entries, so warnings vanish on the next build |
| C. A `validate:features` rule only | the CLI | Deterministic in CI, but the CLI cannot read `astro.config`, so the verb list must be passed again as flags |
| **D. One pure core, two callers** | `lintSteps(view, {rules, file, warn, lineOffset})`, called wherever `warnDuplicates` is | One rule set, no split. Includes stay silent, as ADR-0051 already decides |

The core needs two additions to `StepView` (`src/lib/gherkin/view.mjs:83-92`):

- a `line`;
- a resolved `keywordType`, so that `And`, `But` and `*` take the type of the
  step before them, Background steps included.

Matching runs only on `text` segments, so the contents of quoted arguments,
placeholders, doc strings, data tables and Examples cells are never scanned.
`keywordType` is the same in every dialect, but the verb list is English. The
parser honours `# language:` (`src/lib/gherkin/fragment.mjs:82-86`), so the
lint should skip non-English features and the docs should say so.

### Config and API surface

```js
gherkin: {
  lint: {
    imperativeSteps: false              // default
      | true
      | { verbs?: string[],             // replaces the default list
          extend?: string[],            // appends to it
          keywords?: ('context' | 'action' | 'outcome')[] },
  },
}
```

- **The key stays out of the page keys.** `lint` goes in `GHERKIN_OPTION_KEYS`,
  not `GHERKIN_PAGES_KEYS`. The lint never changes generated bytes, so it needs
  no drift parity.
- **CLI linting is optional.** If CI should lint too, that takes an optional
  `--lint-imperative` flag on the CLI, which is a duplicated setting, or a data
  file both paths read.
- **Warnings go to `warn`, never `recordFatal`.** Proposed format:
  `[dk-gherkin] features/x.feature:14 step "When I click …" names a UI action ("click") — describe the behaviour instead; silence with @dk:allow=imperative`.
- **Suppression is a contract change.** A per-scenario opt-out, such as
  `@dk:allow=imperative` at Feature, Rule or Scenario level, would change the
  `@dk:` contract in three ways:
  - `METADATA_KEYS` is closed and warns on unknown keys
    (`src/lib/gherkin/feature-core.mjs:64-74,287-292`).
  - ADR-0046 gives `@dk:` meaning only at Feature level.
  - The fence stage warns that `@dk:` tags have no effect (`gherkin-fence.ts:530`).

  Comments cannot carry the opt-out, because they do not reach the view.

### Recommendation

Option D, off by default and warn-only. Use the narrow phrase-anchored English
list plus the selector signal, with `context` and `action` steps as the default
scope. Record a short ADR that closes the ADR-0046 follow-up and covers the
suppression tag. Update `authoring.md`.

**Size: S–M.** That is about 150–250 lines across `view.mjs`, a new
`gherkin/imperative.mjs`, `options.mjs`, the fence hook and `feature-core.mjs`,
plus about ten tests. The tests should cover:

- a step that is flagged;
- a step that is clean;
- a domain counter-example;
- a Dutch feature, which is skipped;
- an outline placeholder;
- a suppressed scenario;
- byte-identical pages with the lint on and off.

## #197 Per-folder default glossary context

### The problem, with live evidence

Today a feature page gets `glossary_context` only from a `@dk:context` tag, which
is single-valued and first-wins (`feature-core.mjs:65-78,362-363`). The example
shows both sides of the problem:

- **Repetition.** All three shipping features repeat `@dk:context=shipping`.
- **A live collision.** `example/features/hr/request-leave.feature` has no tag,
  and the glossary defines `policy` in both `shipping` and `hr`
  (`example/.contextive/definitions.yaml:30,39`). So "leave policy" on that page
  is an unresolved collision today.

### Prior art

- **Contextive already maps paths to contexts.** Each context in a Contextive
  glossary can take `paths:` globs, and its terms are shown for files that match.
  doc-kitty adopts the Contextive schema but drops `paths`
  (`src/lib/glossary/types.ts:26-30`). However, Contextive's semantics are
  many-to-many visibility: a file can match several contexts. #197 needs a single
  context for disambiguation, so `paths` would need a tie-break rule to serve as
  the default. The orchestrator therefore treats it as a secondary option.
- **Serenity BDD derives requirement tags from folder hierarchy.** It adds the
  folder's requirement and every parent's, with no override
  (`FileSystemRequirementsTagProvider.java:209-238`). That is the closest
  folder-to-metadata precedent.
- **Cucumber tag inheritance stays inside one file.** No runner derives tags from
  directories.
- **The precedent in this repo is `gherkin.titles`.** `gherkin.titles`
  ([ADR-0054](../../adr/0054-gherkin-draft-hubs-titles-and-scenario-route.md)) keys directories
  relative to their source, matches exactly, and warns on a key that matches no
  feature directory (`generate.mjs:375-379`). Its CLI twin is
  `--titles dir=Label`.
- **ADR-0028 rejected inheritance for v1.** It rejected making `glossary_context`
  inheritable from a section default ("a hidden data path … Revisit on demand";
  `docs/adr/0028-glossary-frontmatter-fields.md:98-101`). #197 reopens that.

### Design options

- **Where the default resolves.** Resolve it at code generation only, inside
  `buildFrontmatter`, as `meta.context ?? folderDefault`. That keeps the pure core
  as the one owner of the mapping from tags to frontmatter (ADR-0046 decision 8).
  The value lands in committed frontmatter, so the auto-linker
  (`glossary-autolink.ts:82-85`), the scenario index (`scenario-index.ts:146,311`),
  `/api/pages` and `llms.txt` all get it with no new readers. The data path stays
  visible, which answers ADR-0028's objection for generated pages.
- **Fences and includes need nothing.** The fence stage runs after the glossary
  and never links terms in step text (ADR-0051 decision 2). The host page's
  context is the author's own frontmatter, so a second resolver there would have
  no visible effect.
- **The match rule is an open choice.** Either an exact directory, like `titles`,
  or the longest prefix by path segment, so that `ship` never matches `shipping`
  and `shipping/eu` overrides `shipping`. Prefix inheritance is what bounded
  contexts suggest.
- **The source of truth is an open choice.** Either a new `gherkin.defaultContext`
  map, which is size S and mirrors `titles`, or the Contextive `contexts[].paths`.
  The second needs a loader change, glob matching and a tie-break, so it is S–M.

### Config and API surface

```js
gherkin: { defaultContext: { shipping: 'shipping', hr: 'people', 'shipping/eu': 'customs' } }
```

- **It is a page key.** It changes generated bytes, so it goes in
  `GHERKIN_PAGES_KEYS`. That requires:
  - a repeatable CLI flag `--default-context <dir>=<ctx>`, copying `--titles`
    (`generate-feature-pages.mjs:80-87,164,230-253`);
  - updated `package.json` scripts;
  - an updated example config and parity test.
- **Validation copies `checkTitles`** (`options.mjs:292-334`): relative POSIX
  keys and the `__proto__` guard. Values must be non-blank. Setting the option
  without `sources` throws.
- **One known duplication remains.** The example config is now mirrored in CLI
  flags for both `titles` and `defaultContext`. The parity test pins this, so it
  is accepted debt.
- **A pre-existing stamp gap.** The generator stamp hashes source bytes only
  (`src/lib/generator-stamp.mjs:172-178`). A change made only in config rewrites
  `glossary_context` but keeps `generated.at`. `sourceUrlPrefix` already has the
  same gap.

Three gaps sit next to this change:

- **An unknown context is never reported.** The schema comment promises "a build
  warning in the plugin layer" (`src/lib/schema.ts:276`), but nothing in
  `src/lib` warns about an unknown `glossary_context`. The page just gets the
  cross-context collision warning indirectly. The architecture lens thought a
  warning existed; the requirements lens was right.
- **An empty tag has no defined fallback.** A valueless `@dk:context=` is warned
  and ignored today (`feature-core.mjs:298-300`). It is unspecified whether the
  folder default then applies.
- **The name collides with existing terms.** "context" is also a section `type`
  and, under #196, a step keyword type. `defaultGlossaryContext` would be
  unambiguous.

### Recommendation

- A `gherkin.defaultContext` map (or `defaultGlossaryContext`) resolved at code
  generation, generated pages only.
- Segment-wise longest-prefix matching. Tag over folder default over none.
- An empty tag falls back to the folder default.
- A build warning for unknown context values, from both map values and tags,
  which closes the ADR-0028 promise.
- A short ADR in the ADR-0054 style that amends ADR-0028's "not inherited" rule
  for generated pages only. The consumer-setup guide gains a row.

**Size: S.**

## #198 Specification layout

### What a feature page shows today

- **Header.** Starlight's `<h1>` and the metadata band, which shows status pill,
  updated date and description (`src/components/PageTitle.astro:67,95-110`).
- **Scenario list.** The right-hand "On this page" table of contents. Rules are
  H2 and scenarios H2/H3 (`render.mjs:12-14`). Examples are deliberately not
  headings, so the table of contents is already a scenario list.
- **Results.** ADR-0055 badges after each scenario heading. They are
  token-styled and signal status with a word, not colour
  (`src/styles/dk-components.css:438-501`).
- **Tags and source link: not shown to readers.** No component reads `data.tags`
  except `Persona.astro`. `sources` reaches only the agent payload
  (`src/lib/routes/agent-page.ts:96`, `src/lib/docs-index.ts:268`) and the
  scenario index.
- **Drafts: invisible.** `@wip` sets `doc_status: draft`
  (`feature-core.mjs:357-358`). That keeps the page out of hubs and adds
  `noindex`, but a draft page renders no band (`MetadataBand.astro:11`,
  `showBand = isPublished`). With drafts published (the default), a `@wip`
  specification looks exactly like an active one. The same gap affects every
  draft page, not only feature pages.

### Prior art

Living-documentation tools agree on three things:

- The header carries tags, then the title, then the description.
- The source location sits near the header.
- Scenarios run inline, with status as text.

The tools checked were Cucumber's HTML formatter, Pickles, Serenity, and
`gherkin-results.md`. None puts a separate scenario rail beside the body.

Starlight 0.42.6 shows a draft notice (`DraftContentNotice`, built on
`ContentNotice`) only for its own `draft` field. DocKitty uses `doc_status`
instead, so the notice must be driven from that. Starlight's `banner`
frontmatter is site chrome outside the token bridge (`src/styles/theme.css:205-214`).
Using it would also mean code generation writes into frontmatter, so it was
rejected.

### Design options for the scenario list

| Option | Verdict |
|---|---|
| (a) Add status and tags to Starlight's table of contents | Rejected. It means changing Starlight's TOC markup, which the rail work deliberately avoids (`collapsible-toc-rail.md`). Below 72rem the TOC becomes a dropdown and the status would be lost |
| (b) A dedicated scenario rail that replaces the TOC | Rejected. It duplicates navigation, breaks the rail geometry assertions, and conflicts with #104's "no duplicate outline" |
| **(c) A header spec card, keeping the TOC as the scenario list** | Recommended by all four lenses that weighed it |

The spec card is one `<section aria-labelledby>` inside the content frame. It is
a region, not a `nav`. It holds:

- the narrative;
- tags as a `<ul>` of chips;
- a real "View source" link;
- an optional results summary that reuses `.dk-gherkin__results`;
- a draft notice when `doc_status` is `draft`.

The draft notice is static text: "Draft — this specification is work in progress
and may change". It must not use `role="alert"` or `role="banner"`. A
scenario-level `@wip` stays a chip, as ADR-0046 already decides
(`docs/adr/0046-gherkin-feature-pages.md:153-154`).

```text
Desktop (≥72rem)                                        Narrow (390px)
┌sidebar┐┌──────────── content ───────────┐┌On this page┐  ┌────────────────────┐
│       ││ <h1> Book a consignment        ││ Background │  │ [On this page ▾]   │
│       ││ [active] updated · description ││ Rule: …    │  │ <h1> Book a …      │
│       ││┌ section "Specification" ─────┐││  Scenario  │  │┌──────────────────┐│
│       │││ ⚠ Draft — work in progress   │││ Rule: …    │  ││ ⚠ Draft — …      ││
│       │││ As a shipper / I want / …    │││  Outline   │  ││ narrative        ││
│       │││ Tags: (FR-003) (shipping)    │││            │  ││ (FR-003)(shipping││
│       │││ Source: features/…/x.feature │││            │  ││ Source: …/x.     ││
│       │││ Results: ✓3 passed ✗1 failed │││            │  ││ Results: ✓3 ✗1   ││
│       ││└──────────────────────────────┘││            │  │└──────────────────┘│
│       ││ ## Background …                ││            │  │ ## Background …    │
└───────┘└────────────────────────────────┘└────────────┘  └────────────────────┘
```

### Wiring and config surface

- **Registration.** Register
  `Specification: '@spec-kitty/doc-toolkit/layouts/Specification.astro'` as a
  base kind beside `Hub` (`manifest.ts:72-74`). Themes merge over it
  (`manifest.ts:96-99`), and that per-kind override is the opt-out, so no new
  option is needed.
- **Layout behaviour.** The layout wraps the content slot rather than
  re-rendering the body, so the ADR-0055 results overlay stays valid
  (`gherkin-fence.ts:730-733`). It must degrade when `sources` or `generated` is
  absent, because authored pages can also say `kind: Specification`.
- **Where the card goes.** The card sits at the top of the layout, below the H1
  and band. That keeps one place where layouts resolve. Moving tags into the
  true page header would need a second `kind` branch in `PageTitle`, extending
  the Persona exception (`PageTitle.astro:68`).
- **Tokens only.** Use the existing `--dk-*` tokens: spacing, radius, text,
  surface and border, `--dk-color-warning` / `-bg` for the draft notice, and the
  badge's success and danger colours. No new tokens are needed. A semantic alias
  `--dk-color-draft` would give #104's token table a named row. No raw colours
  and no `--sl-*` in new CSS.
- **ADR.** A new ADR. It reverses ADR-0046's "no new render code" consequence
  and adds a structural-kind layout under ADR-0011/0013/0015.

### Test lanes: what "passes the existing lanes" would prove

- **The geometry lane would prove nothing today.** Axe already scans the
  generated feature page (`tests/a11y/routes.ts:98-103,410-414`). But the
  geometry lane's scroll routes are home, hub, chapter, glossary demo and
  persona (`tests/a11y/layout-geometry.spec.ts:433-439`). The requirements lens
  read the axe coverage as covering both; the source shows it does not.
- **Required additions.** The mission must add the feature page and a draft
  feature page (`/behaviour/shipping/track-consignment/`) to the geometry
  routes, and the draft page to the axe routes. It should also add a test that
  greps the layout CSS for literal colour and spacing values.

### Dependency on #104

Issue #104 is `status:blocked`, and its `--sk-*` → `--dk-*` bridge is unsettled. So
"uses design tokens only" can only mean today's `--dk-*` tokens. A fifth layout
joins #104's migration list (Article, Hub, Persona, Presentation).

### Recommendation

Option (c), on by default for `kind: Specification` through the base manifest,
with a theme opt-out. Drive the draft notice from `doc_status`, not the consumed
`@wip` tag. That covers `@dk:status=draft` and malformed statuses that fail
closed to draft (`feature-core.mjs:250-253`). Amend #198's "scenario list beside
the body" to "the table of contents is the scenario list".

**Size: M.** One layout file, about 60 lines of token-only CSS, a manifest
entry, the lane additions, visual baselines, an ADR and docs. The lanes and
baselines dominate.

## Decisions for the operator

The operator decided all thirteen on 2026-10-19 and took the recommendation
each time. The table below keeps the options as they were put. The operator
also asked for all three side findings to be handled in the same run: fix the
stale pointer, and file issues for the other two.

| # | Issue | Question | Options | Recommendation, decided |
|---|---|---|---|---|
| D1 | #196 | Which surfaces are linted? | (a) generated pages only; (b) generated pages and in-page fences, includes silent; (c) also a `validate:features` report | (b). Optionally a CLI flag later |
| D2 | #196 | How broad is the default list? | (a) narrow, phrase-anchored, plus selector signal; (b) broad, including enter, select and submit; (c) actor-anchored regex | (a). Ambiguous verbs documented for `extend` |
| D3 | #196 | Which keyword types by default? | (a) context and action; (b) all three | (a), configurable through `keywords` |
| D4 | #196 | Add a suppression tag now? | (a) `@dk:allow=imperative` at Feature, Rule or Scenario (contract change, ADR); (b) none in v1 | (a) |
| D5 | #197 | Where does the folder default come from? | (a) `gherkin.defaultContext` map; (b) Contextive `contexts[].paths` with a tie-break | (a). Document the relationship to `paths` |
