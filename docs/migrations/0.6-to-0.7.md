# Upgrading from 0.6.0 to 0.7.0

Two areas ask something of you. The PlantUML include check is stricter when you
run it with `--service-container`; the OpenAPI option publishes new agent
entries and new input keys, and refuses one label shape it used to accept
silently. A site that sets neither `openapi` nor the PlantUML flag changes
nothing. The [changelog](../../CHANGELOG.md) has every change in full.

Each failure below starts with the symptom, then the fix. The guides explain
the rules in [What the check verifies](../guides/consumer-setup.md#what-the-check-verifies-and-how-it-fails)
and [Publish OpenAPI reference pages](../guides/openapi-reference.md).

## The profile is missing or not SANDBOX

Symptom: `FAIL — opt-in unset (sandbox), but the service's PLANTUML_SECURITY_PROFILE is not set`.

Fix: set `PLANTUML_SECURITY_PROFILE=SANDBOX` on the service. A missing
variable counts as the image default, `INTERNET`. If the service should fetch
remote includes, declare
[the opt-in](../guides/consumer-setup.md#allowing-external-includes) instead.

## A PlantUML setting sits where the check cannot read it

Symptom: a FAIL naming a `-D` property, a `plantuml.*` environment key or
`PLANTUML_PROPERTY_FILE`.

Fix: remove it and set `PLANTUML_SECURITY_PROFILE` and
`PLANTUML_ALLOWLIST_URL` as environment variables. Only these names fail:
`plantuml.security.profile`, `plantuml.allowlist.url`,
`plantuml.property.file` and `plantuml.include.path` (any case, `.` or `_`).
Tuning such as `-DPLANTUML_LIMIT_SIZE=8192` still passes.

## A Java `@argfile` is present

Symptom: a FAIL naming an `@argfile` in a Java-options value or a command-line
argument.

Fix: move the options out of the file into the two environment variables, and
drop the `@` word.

## `--server` points at a port the container does not publish

Symptom: a FAIL saying the container does not publish the `--server` port.

Fix: publish the port on a matching address (`-p 8091:8080`, or
`-p 127.0.0.1:8091:8080` with `--server http://127.0.0.1:8091/svg/`), and name
the container that serves `--server`.

## A flag has an empty value

Symptom: exit code 2 after `--service-container ""` or another empty value,
often from an unset shell variable.

Fix: pass a value, or leave the flag out.

## The `openapi` option

### Dotted version labels now fail the build

Symptom: `[dk-openapi] specs[0] "v1.1": label may not contain "." …` on a
configuration that built before.

Fix: rename the label to a route-safe one (`v1-1`). The renderer always
dropped dots from routes, so the old label advertised an address the site never
served; 0.7.0 refuses it instead. Derived labels from `archive.labelPattern`
follow the same rule. Labels may use `a-z`, `0-9`, `_` and `-`. Every `section`
segment follows the same rule: `reference/v1.1` is refused; write
`reference/v1-1`.

### Unreleased versions leave the sitemap and search

Symptom: fewer URLs in `sitemap-index.xml` and fewer search results: the pages
of every spec version with `released: false` are gone from both.

Fix: none needed for the pages — they are still built and served, carry the
"unreleased" badge, and appear in `llms.txt` and the agent surfaces. If you
want a version discoverable, mark it `released: true`.

### New agent entries in `/api/index.json`

Symptom: consumers of the agent API see new records: one per spec version,
appended after the docs records, with `type: "reference"`,
`doc_status: "active"`, `kind: "Reference"`, `tags: ["openapi"]`, plus the
OpenAPI-only `released`, `rawDocumentUrl` and `sha256`. The per-page payload
`/api/pages/<section>/<label>.json` carries the same fields. The docs records
and their ranking are unchanged. The `buildId` is unchanged for a site
without `openapi`; with it, the `buildId` now also covers each spec
version's identity, so it changes when a spec changes.

Fix: none. Filter on `type` or `tags` if the new records are noise for you.
Unreleased versions are marked `released: false` and "(unreleased)" in the
title.

### New opt-in keys

0.7.0 accepts new input shapes behind keys that did not exist before; none of
them change an existing site's output:

- `openapi.specs[].url` with `sha256` — a pinned `https` definition, fetched
  once per build and cached under `node_modules/.cache/doc-kitty/openapi/`.
- `openapi.archive` (`glob` + `labelPattern`) — one version per matched file.
- `openapi.llmsOperations` (default `false`) — operation lines in `llms.txt`.
- `openapi.offline` (or `DOCKITTY_OFFLINE=1`) — no network requests; the
  remote cache or a closed failure.

See [the guide](../guides/openapi-reference.md) for the full contract, and
[ADR-0078](../adr/0078-openapi-surface-matrix.md) for the surface decisions.
