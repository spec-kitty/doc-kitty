# Upgrading from 0.3 to 0.4

For an adopter whose site uses `@spec-kitty/doc-toolkit` 0.3.0. Toolkit 0.4.0
moves to Astro 7 and Starlight 0.42 and removes what 0.3.0 deprecated. Pages
render as they did. Work through the steps in order; the
[changelog](../../CHANGELOG.md) has each change in full.

## 1. Use Node 22.22 or later

The toolkit declares `engines.node: ">=22.22.0"`. Update your local Node, the
`node-version` of every CI job that builds the docs, and any `engines` field of
your own.

## 2. Install the new versions

```sh
pnpm add @spec-kitty/doc-toolkit@^0.4.0 astro@^7.4.0 @astrojs/starlight@^0.42.6 @astrojs/markdown-remark@^7.3.3
```

`@astrojs/markdown-remark` is a new peer dependency: the toolkit sets Astro's
Markdown processor to its `unified()` processor
([ADR-0060](../adr/0060-markdown-processor-unified-for-astro-7.md)).

## 3. Check your Astro config

- **Do not set `markdown.processor`.** The toolkit sets it to `unified()` before
  any plugin is added. Astro 7's default processor drops every remark and
  rehype plugin.
- **Your own remark and rehype plugins keep working.** Plugins you list in
  `markdown.remarkPlugins` or `markdown.rehypePlugins`, or that your own
  integration appends with `updateConfig`, run on the `unified()` processor in
  the same order as before. Integrations that set a processor themselves are
  not supported.
- **`compressHTML` is set by the toolkit.** It pins `compressHTML: true`, the
  pre-Astro-7 whitespace output, and overrides a value in your config.
- **Heading anchor links stay off.** Starlight now adds them by default; the
  toolkit turns them off for parity. To turn them on, pass
  `starlight: { markdown: { headingLinks: true } }` to
  `defineDocKittyIntegrations`.
- **Code outside the toolkit.** Your own components, pages or Starlight
  overrides may need changes for Astro 7 and Starlight 0.42; see their upgrade
  guides. The toolkit's own overrides and routes are already updated.

## 4. Regenerate generated pages

The 0.3.0 generator stamps (`generated.by: doc-kitty/gherkin` or
`doc-kitty/glossary`, or a `sha256:` hash in `generated.at`) are retired, and
`dockitty-validate-frontmatter` fails a page that still carries one.

- Gherkin feature pages: run `dockitty-generate-feature-pages` with the
  arguments you already use.
- Glossary pages: run `astro build` (or `astro dev`); the build rewrites them.

Commit the regenerated pages. Each now carries
`generated: { by: <producer>/0.4.0, at, content_hash }`.

## 5. Update API clients

- **Scenarios API** (`api/scenarios.json`): `version` is `"2"` and
  `generated_from` is gone. Read the producer from `generated_by`
  (`doc-kitty-gherkin/<version>`).
- **Agent API** (`api/index.json`): `version` is `"3"`, and each page's
  `updated` is a full UTC timestamp such as `2026-10-18T00:00:00Z`. A client
  that pins version `"2"` or parses a date-only value needs updating.

## 6. Build and check

```sh
pnpm exec dockitty-validate-frontmatter docs
pnpm build
```

Astro 7 stops the build at the first docs page with invalid frontmatter, so
run the frontmatter check first to see every problem at once. Render errors,
such as a broken Gherkin fence, also stop the build at the first page and the
frontmatter check does not catch them, so fix them one build at a time. Two kinds of
warning are expected on every build and are harmless: a missing `i18n`
collection, and one route conflict per deck page under `/presentations/`.

If your site sets `gherkin.results`, a missing results report now fails the
build in CI (see the changelog's 0.4.0 Breaking section). Produce the report
first in the same job, or set `gherkin.results.required: false` for jobs that
never run the tests.
