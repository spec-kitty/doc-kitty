# ADR-0052: Theme slot names are checked when the config loads

## Status

Accepted (2026-10-14).

Supersedes in part: the "Slot names are checked by TypeScript only" known
limitation of [ADR-0044](./0044-header-carrier.md).

## Context

A theme fills `dk:` slots by name (ADR-0011). The names were a TypeScript
type, `DkSlotName`, and nothing else. A site's `astro.config.mjs` is plain
JavaScript, and no build step type-checks it. A misspelt name such as
`dk:site-heading` was merged, carried in the generated manifest under a name
no carrier reads, and the stock component rendered. The build printed nothing.

ADR-0044 recorded this as a known limitation. It became easy to hit once a
theme could replace the whole site header (issue #114).

## Decision

1. The slot names are declared once, as the runtime list `DK_SLOT_NAMES` in
   `theme.ts`. `DkSlotName` is derived from that list.
2. `resolveTheme` rejects every slot key outside the list, in every layer of
   the `extends` chain. It throws one error that names the unknown slot, the
   theme's `name` when it has one, and all valid slot names.
3. The check fails the build. It does not warn.

`defineDocKittyIntegrations` calls `resolveTheme` while the config file is
evaluated, so the error appears before any page is built, in `astro build` and
in `astro dev`.

## Consequences

### Positive

- A misspelt slot name is reported where it is written, with the fix in the
  message.
- The type and the runtime check cannot drift: both read one list.
- Theme authors meet one rule for theme mistakes. `resolveTheme` already
  throws on a `--sl-*` token (ADR-0011).

### Negative

- A site whose theme names an unknown slot stops building after the upgrade.
  That site was already rendering the stock component in place of the one its
  author wrote, so the build error replaces a wrong page, not a correct one.
- Adding a slot now means adding it to `DK_SLOT_NAMES`, not only to the type.
  The type is derived, so there is one place to change.

### Risks

- A theme generated by a tool that adds keys of its own to `slots` would stop
  building. None is known.

## Alternatives considered

### Option A: Warn and continue

A build-log warning keeps every existing site building. It was not chosen:
the site it warns about still ships the wrong component, and a warning in a
long build log is easy to miss, which is how the defect stayed silent.

### Option B: Check in the manifest generator

`generateManifestSource` sees the merged slots too. It was not chosen: the
merged result no longer says which layer held the bad name, and the error
would surface later in the build.
